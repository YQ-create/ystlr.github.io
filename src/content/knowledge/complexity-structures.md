复杂度描述的不是「跑了几毫秒」，而是**输入规模变大时耗时/空间怎么增长**。写代码时能用它做一个很实用的判断：这段逻辑在 100 条数据上没问题，到 10 万条会不会突然不可用。

## 大 O 速查

| 复杂度 | 典型代码 | n=1000 时的量级 |
| --- | --- | --- |
| `O(1)` | 数组按下标取、哈希查找 | 1 |
| `O(log n)` | 二分查找、平衡树 | ~10 |
| `O(n)` | 一次遍历 | 1,000 |
| `O(n log n)` | 高效排序 | ~10,000 |
| `O(n²)` | 两层嵌套遍历、冒泡排序 | 1,000,000 |
| `O(2ⁿ)` | 穷举子集 | 别让它进生产代码 |

```js
// O(n)：单层循环
const hasDraft = notes.some(n => n.draft);

// O(n²)：每个元素都和其余元素比一次
for (const a of notes) for (const b of notes) { /* ... */ }

// O(n)：先建索引，把「查找」从 O(n) 降到 O(1)
const byId = new Map(notes.map(n => [n.id, n]));
const found = byId.get(targetId);
```

估算时的三条经验：**只看最高阶项**（`2n² + 3n` 记作 `O(n²)`）、**常数系数忽略**（两次遍历仍是 `O(n)`）、**嵌套相乘、顺序相加**。

## 常见数据结构对照

| 结构 | 访问 | 查找 | 插入/删除 | 适合 |
| --- | --- | --- | --- | --- |
| 数组 | `O(1)` 按索引 | `O(n)` | 尾部 `O(1)`，中间 `O(n)` | 遍历、按下标取、有序列表 |
| 链表 | `O(n)` | `O(n)` | 已知节点 `O(1)` | 频繁在中间插删（JS 里少用） |
| 栈（LIFO） | — | — | `O(1)` 压/弹 | 撤销、括号匹配、DFS |
| 队列（FIFO） | — | — | `O(1)` 入/出 | BFS、任务排队 |
| 哈希表 / Map | — | 均摊 `O(1)` | 均摊 `O(1)` | 按 key 查、去重、计数 |
| 二叉搜索树 | — | 平均 `O(log n)` | 平均 `O(log n)` | 需要有序 + 动态增删 |
| 堆 | 顶 `O(1)` | — | `O(log n)` | 前 K 大、优先队列 |

**JS 里的现实约束**：V8 的数组在稀疏/混类型时会退化成字典模式，「按下标 `O(1)`」的前提是密集数组；`Array.prototype.shift()` 要搬移后面所有元素，是 `O(n)`，拿数组当队列在大批量场景下很慢，改用双指针或专门实现的队列。

## 用结构换个思路

```js
// 需求：统计每个分类下的笔记数
// 写法 A：每条笔记都遍历一次分类列表 → O(n × m)
// 写法 B：一次遍历，用 Map 累加 → O(n)
const counts = new Map();
for (const note of notes) {
  counts.set(note.category, (counts.get(note.category) ?? 0) + 1);
}

// 需求：判断两个列表有没有交集
const left = new Set(idsA);
const overlap = idsB.filter(id => left.has(id));  // O(n + m)
```

多数「算法优化」其实是**换一个查找结构**：把反复的线性查找换成哈希，把有序数据上的查找换成二分，把嵌套循环换成一次预处理。

## 时间与空间的取舍

| 做法 | 省了什么 | 多了什么 |
| --- | --- | --- |
| 建索引 / Map | 时间 | 内存 |
| 缓存中间结果 | 重复计算 | 内存 + 失效逻辑 |
| 原地排序 | 内存 | 会破坏原数组顺序 |
| 流式处理 | 内存 | 不能随机访问、代码更复杂 |

小数据量下，可读性比理论最优更重要；只有在数据规模确实会增长、或已经测出瓶颈时，才值得引入更复杂的数据结构。

## 容易踩的坑

- **把「平均」当成「一定」**：哈希表在最坏情况下会退化到 `O(n)`，平衡树之所以重要就是它给出了更稳的上界。
- **忽略隐藏的 `O(n)`**：`includes`、`indexOf`、`shift`、`unshift`、展开运算符在循环里都会把整体复杂度抬一阶。
- **`JSON.parse` / 序列化计费漏算**：数据转换常常比算法本身更贵。
- **用递归不设深度上限**：树退化成链时栈溢出，且 JS 没有尾调用优化保证。
- **重复计算 `arr.length` 之外的值**：循环体里反复做同一份预处理，移到循环外。
- **只看时间不看空间**：一次生成几万个中间对象，GC 压力会让「理论上更快」的写法实测更慢。
- **在小数组上过度优化**：几十条数据里 `O(n²)` 常常比建 HashMap 还快，先测量再改。
